# Verba

Workplace Chinese–English translation interface with email and colleague-chat modes.

## Run locally

1. Copy `.env.example` to a new local file named `.env`.
2. Replace `your_api_key_here` with a real OpenAI API key beginning with `sk-`. Do not use Chinese placeholder text and do not place the key in frontend files.
3. Add one or more provider API keys, then start the local server:

```powershell
node server.mjs
```

Open `http://localhost:3000`.

## Windows desktop app

Build a Windows NSIS installer with desktop and Start menu shortcuts:

```powershell
pnpm install
pnpm dist
```

The installer is written to `dist`. In the desktop app, use the **API keys** item in the left sidebar to save OpenAI, Gemini, or DeepSeek keys. Saved keys take effect immediately and remain only in the local Verba configuration.

The translation endpoint returns a context-aware translation plus an English meaning check. If the key is missing or invalid, the app gives a configuration message instead of exposing a low-level request-header error.

## API providers and glossary

Open **API keys** in the app to choose OpenAI, Google Gemini, or DeepSeek. The desktop app saves keys to its local configuration `.env`; keys are never placed in frontend files.

Verba never relies on an unverified hard-coded model as its default. After an API key is saved, it discovers models from that provider account, filters for stable low- or medium-cost text models, and runs a minimal JSON-format health check. The verified model choice and health state are stored only in local `model-state.json` data. Open **API settings** to see the selected model, check its status, force a recheck, or enable a manual override. Model names do not need to be added to `.env`.

Open **Glossary** in the sidebar to edit the mandatory glossary. Each `source term → required translation` pair is stored locally in the browser, included in every request, and the model is instructed to use it exactly.

## Updates and history

The desktop app checks for updates at startup. Open **Settings** in the lower-left sidebar to manually check, see download status, and restart to install a downloaded update. Updater event logs are written to the console and to `%APPDATA%\\Verba\\logs\\updater.log`.

Updates are served from [GitHub Releases](https://github.com/guanchengwang11-ux/Verba/releases). The app uses `electron-updater` with the GitHub provider and reads the `latest.yml` asset automatically generated by electron-builder. The repository and releases must remain public; installed desktop clients do not contain a GitHub access token.

### Automated releases

The workflow at `.github/workflows/release.yml` runs whenever a tag matching `v*` is pushed. It checks that the tag version matches `package.json`, builds the Windows NSIS installer, creates or updates the GitHub Release, and uploads these update assets:

- `Verba-Setup-<version>.exe`
- `Verba-Setup-<version>.exe.blockmap`
- `latest.yml`

No custom GitHub secret is required for this workflow. It uses GitHub Actions' built-in `GITHUB_TOKEN` with `contents: write` permission. Do not create or store a personal access token unless your repository policy explicitly prevents the built-in token from creating releases.

Optional code-signing secrets for production Windows releases are `CSC_LINK` (base64 certificate or certificate URL) and `CSC_KEY_PASSWORD` (certificate password). Add both only after obtaining a code-signing certificate; the workflow functions without them, but unsigned installers can prompt Windows SmartScreen warnings.

### First release

1. Update the `version` field in `package.json` to the release number, for example `1.0.2`.
2. Commit and push the code to `main`.
3. Create and push an exactly matching tag: `git tag v1.0.2` then `git push origin v1.0.2`.
4. Wait for the **Publish Verba for Windows** GitHub Actions workflow to finish, then confirm the three assets appear in the new GitHub Release.
5. Install an older Verba version, open **Settings**, and choose **Check for updates** to test download and restart-to-install.

Every successful translation is saved locally. Use **History** in the sidebar to search original text, translated text, or the English meaning check, then select an item to restore it to the translator.
